# ThreatIntel Operations Runbook

## Daily development start and stop

From the repository root, start the API and local PostgreSQL:

```bash
./start_backend.sh
```

In a second terminal, start the dashboard:

```bash
cd frontend
npm run dev -- --host 127.0.0.1 --port 5177
```

The Wazuh reverse tunnel starts with the backend when the Ubuntu VM is reachable. Stop foreground services with `Ctrl+C`; stop its standalone tunnel with `./stop_wazuh_tunnel.sh`. The dashboard is at `http://127.0.0.1:5177` and API docs are at `http://127.0.0.1:8006/docs`.

## Feed refresh control

The dashboard Automation control pauses scheduled feed/API refreshes. A manual run obeys that pause; an intentional one-off refresh uses:

```bash
cd backend
./run_pipeline.sh --force
```

## Wazuh integration

The Ubuntu Wazuh manager calls its `custom-threatintel` adapter for alerts at level 7 or higher. The adapter signs requests with the dedicated SIEM token and sends them through this reverse path:

```text
Wazuh VM 127.0.0.1:18006 -> SSH reverse tunnel -> Kali 127.0.0.1:8006/siem/ingest
```

Useful checks:

```bash
systemctl --user status threatintel-wazuh-tunnel.service
curl -fsS http://127.0.0.1:8006/auth/config
```

The automatic path was verified on 2026-10-09 with a genuine Wazuh rule `5712`, level `10` alert generated by repeated SSH attempts against a nonexistent test user. It appeared as SIEM event 17. A match count of zero is valid for an authentication-only event containing no IOC or CVE; events with exact stored observables create `siem_matches` rows.

## Automatic startup

Install the two user services (API/database launcher and resilient Wazuh tunnel):

```bash
./scripts/install_user_services.sh
systemctl --user status threatintel-api.service threatintel-wazuh-tunnel.service
```

They start when the user session starts. To start before interactive login, an administrator may enable lingering once with `sudo loginctl enable-linger "$USER"`. Roll back with:

```bash
systemctl --user disable --now threatintel-api.service threatintel-wazuh-tunnel.service
```

## HTTPS deployment

1. Put the certificate and private key at `/etc/nginx/ssl/threatintel.crt` and `/etc/nginx/ssl/threatintel.key` with restrictive permissions.
2. Replace `threatintel.local` in `deploy/nginx/threatintel.conf` if using another DNS name.
3. Build and install:

```bash
cd frontend
npm run build
cd ..
./scripts/install_nginx.sh
```

The installer refuses to continue without certificate files, writes the rendered nginx site, validates it with `nginx -t`, and reloads only after validation. To roll back, remove `/etc/nginx/sites-enabled/threatintel` and reload nginx.

## Backup and restore

Create a PostgreSQL custom-format backup (created with mode `0600` and ignored by Git):

```bash
./scripts/backup_database.sh
```

Restore is intentionally explicit and destructive to existing database objects:

```bash
./scripts/restore_database.sh /absolute/path/to/threatintel_TIMESTAMP.dump --yes
```

Stop application writes before restore, take a fresh backup, restore, then run the smoke and API checks.

## Troubleshooting

- API fails to start: confirm the local PostgreSQL data directory exists at `work/pgdata` and inspect `work/postgres.log`.
- Wazuh alerts do not arrive: confirm the VM is running, the tunnel service is active, and Wazuh Manager is active.
- Dashboard loops on login: verify frontend and backend URLs match, clear an expired `ti_token`, and use a current TOTP.
- AI response falls back: verify `ollama list` contains `llama3.2` and Ollama listens on `127.0.0.1:11434`.
- Enrichment quota pressure: pause Automation in the dashboard; do not run `--force` until quotas reset.
